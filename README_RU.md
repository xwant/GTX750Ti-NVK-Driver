# GTX 750 Ti: эксперимент с кэшем команд NVK

Статус: реальный патч исходного кода, успешная сборка 64-битного NVK без оконных платформ и CPU-тесты. На GTX 750 Ti не запускался. Прирост FPS, снижение физического расхода VRAM и стабильность на GPU пока не подтверждены.

## Подтверждённая конфигурация пользователя

- GM107, PCI `10de:1380`, PCI revision `a2` (не вывод о маркировке кристалла).
- EVGA, subsystem `3842:3751`; VBIOS `82.07.32.00.50`; 2048 MiB VRAM.
- PCIe 8.0 GT/s ×16: в момент диагностики линия не была сужена.
- CachyOS, ядро `7.3.1-1-cachyos`, KDE Wayland.
- NVIDIA proprietary `580.196.07`, OpenGL 4.6, Vulkan DEVICE API `1.4.312`.
- Установлен LTS `6.18.55-2-cachyos-lts` с NVIDIA DKMS; загрузка резервного пункта ещё не проверена.
- Mesa `26.2.6` установлена, но NVK ICD отсутствует; единственный ICD — NVIDIA.
- 801 MiB использовано в снимке NVIDIA: это не доказательство утечки или исчерпания памяти. 823 MHz без записи нагрузки не доказывают троттлинг.
- Повторяются `Failed to allocate NVKMS memory for GEM object`. NVKMS относится к NVIDIA KMS; это не сообщение NVK. Причина по этому журналу не установлена.
- В modprobe-конфигурации два значения TemporaryFilePath; фактически применённое значение нужно читать из `/proc/driver/nvidia/params`. Ни один файл не менялся.

## Основа и патч

Upstream: https://gitlab.freedesktop.org/mesa/mesa

Тег: `mesa-26.2.6`; commit: `8e87a503ebd91408c88596d1b9eeb5f4c0b2088d`.

Ветка: `experiment/gm107-command-cache`. `gm107-command-cache.patch` содержит изменения драйвера, документацию и семь тестовых случаев. Список SHA-256 файлов находится в `SHA256SUMS`.

Параметр `NVK_GM107_CMD_CACHE_LIMIT_KIB=256` включает лимит 256 KiB на свободный LOCAL-capable кэш одного командного пула только у GM107 (chipset 0x117). Размер блока NVK — 64 KiB: остаются максимум четыре блока. Отрицательное или отсутствующее значение сохраняет исходную политику; 0 отключает этот кэш. Значения округляются вниз до целого блока.

Изменения:

1. `nvk_cmd_pool.h`: лимит и счётчик свободных блоков в пуле.
2. `nvk_CreateCommandPool`: проверка чипсета и чтение экспериментального параметра.
3. `nvk_cmd_pool_free_mem_list`: принимает только уже возвращённые блоки. Сохраняет блоки до лимита; лишним снимает ссылку через существующий `nvk_cmd_mem_destroy`.
4. `nvk_cmd_pool_alloc_mem`: уменьшает счётчик при повторном использовании блока.
5. `nvk_cmd_pool_destroy_mem`: обнуляет счётчик при очистке/trim.
6. Тесты вызывают реальный код NVK с имитацией backing memory. Проверяют возврат, освобождение, 1000 циклов повторного использования, trim, уничтожение, независимость активного объекта и GART-кэша.

Живые командные буферы, текстуры, шейдеры, QMD-кэш и GART-кэш не ограничиваются. Синхронизация Vulkan не ослабляется. Для reset/free Vulkan требует отсутствия pending-исполнения и внешней синхронизации пула.

Это НЕ глобальный лимит VRAM. LOCAL-capable BO могут размещаться в VRAM или GART; свободные кэши существуют отдельно в каждом пуле. Новый лимит может увеличить количество выделений и ухудшить frametime. Если приложение не возвращает много таких буферов, эффект может отсутствовать.

## Что проверено здесь

- Debian 13, GCC 14.2.0, Rust 1.90.0, LLVM/Clang 19.1.7, bindgen 0.71.1, cbindgen 0.29.0; дополнительные точные версии — в `logs/`.
- Полная сборка `libvulkan_nouveau.so` с `platforms=[]`, без OpenGL/Gallium. Это полноценная headless-сборка Vulkan-драйвера, но не проверка Wayland/X11 WSI.
- Динамическая загрузка библиотеки с `RTLD_NOW`: успешно.
- `meson test --suite nouveau`: 11/11 PASS, включая 7 новых случаев.
- `vk_cache_probe.c`: компиляция с `-Wall -Wextra -Werror`; запуск завершился кодом 77 (`no usable Vulkan ICD`). Аппаратная часть не выполнена.
- Проверка синтаксиса Bash и контрольный набор данных анализатора frametime: успешно.

В CPU-тесте 512 логических блоков по 64 KiB после возврата сохраняются исходной политикой; с лимитом 256 KiB сохраняются четыре и освобождаются 508. Это тест жизненного цикла имитированных объектов, а НЕ замер 31.75 MiB экономии на видеокарте.

Изолированная среда сборки потребовала указать каталог встроенных заголовков Clang для bindgen и исправить выбор динамической libelf вместо статической. Эти изменения касались только среды сборки. Исходники Mesa для обхода ошибок сборки не упрощались.

## Сборка под CachyOS

Скрипт `build-cachyos.sh` создаёт отдельные деревья исходной и изменённой Mesa, проверяет базовый SHA, собирает NVK с X11/Wayland и выполняет CPU-тесты. Он НЕ вызывает `meson install`, не использует sudo, не меняет DKMS, initramfs, модули, VBIOS, частоты или загрузчик. По умолчанию четыре задачи компиляции; можно задать `GM107_JOBS=2`.

Нужные пакеты разработки: `base-devel git meson ninja rust rust-bindgen cbindgen python-mako python-pyyaml python-packaging llvm clang spirv-llvm-translator spirv-tools libdrm libelf expat zlib zstd wayland wayland-protocols libx11 libxcb libxshmfence libxrandr xorgproto`. Часть уже установлена. Сначала проверяются отсутствующие зависимости; пакетная установка в скрипт намеренно не включена.

После подготовки зависимостей, из распакованного каталога:

```bash
bash build-cachyos.sh
```

Исходники и сборки появятся в `work/`, журналы — в `logs/`. Сборка на CachyOS ещё не запускалась; конкретная комбинация GCC 16/LLVM пользователя пока не проверена. Первый прототип рассчитан на 64-битные приложения; 32-битный NVK не собран.

Исходный SHA, патч, параметры и версии зависимостей фиксируются. Это воспроизводимая процедура, но не обещание побитово одинаковой сборки из rolling-репозиториев: для строгого повторения нужно сохранить те же пакеты/снимок репозиториев. Для данной проверенной сборки есть версии среды и журналы.

## Измерения на карте — после подготовки и подтверждения тестовой загрузки

Нельзя запустить NVK поверх загруженного proprietary NVIDIA простым выбором ICD. Скрипты не переключают kernel driver.

Сравнения:

- **NVIDIA** — текущий пользовательский эталон.
- **base** — исходный NVK 26.2.6.
- **off** — изменённый NVK с выключенным лимитом: контроль накладных расходов патча.
- **cap** — тот же изменённый NVK с лимитом 256 KiB.

Сравнение base/off/cap выполнять на одном и том же ядре Nouveau, при одинаковом состоянии частот, нагрузке рабочего стола, разрешении и настройках. Если Nouveau остаётся на низких частотах, это отмечается отдельно; такой результат не доказывает неэффективность конкретного патча. Выбор pstate без отдельного согласования не выполнять.

### Микротест

`bench/vk_cache_probe` выбирает только `10de:1380`, создаёт 32 MiB командных данных в первом цикле, затем использует меньшие обновления. После каждого submit ждёт fence и проверяет все данные readback. После каждого reset пишет CPU-время записи/ожидания/сброса и доступные значения `VK_EXT_memory_budget`. В конце вызывает trim. Программа не считает FPS.

На текущем NVIDIA после компиляции:

```bash
./bench/vk_cache_probe > logs/nvidia-probe.csv 2> logs/nvidia-probe.txt
```

Пример выбора локального NVK, ТОЛЬКО когда карта уже работает с Nouveau:

```bash
VK_DRIVER_FILES="$PWD/work/mesa-patched/build-gm107/src/nouveau/vulkan/nouveau_devenv_icd.x86_64.json" \
NVK_GM107_CMD_CACHE_LIMIT_KIB=256 \
./bench/vk_cache_probe > logs/cap-probe.csv 2> logs/cap-probe.txt
```

Для контроля убрать переменную лимита; для base выбрать ICD из `mesa-base`. Сначала выполнить отдельный проход с `VK_LAYER_KHRONOS_validation`, если слой установлен. Проходы для времени выполнять без validation. Значения budget/usage — оценка драйвера; одинаковый смысл счётчиков между NVIDIA и NVK не гарантирован.

### Игра

Рекомендуемый первый сценарий: локальный повтор Dota 2, один и тот же участок 120 секунд. Игра и разрешение пользователем ещё не выбраны. Онлайн-матч непригоден для воспроизводимого сравнения.

```bash
bash bench/run-game.sh nvidia run01 /путь/к/игре аргументы
```

Для Steam можно поставить в параметры запуска абсолютный путь к `run-game.sh`, затем `nvidia run01 %command%`. Для каждого запуска нужен новый run ID. После загрузки и прогрева нужной сцены нажать левый Shift+F2. Wrapper записывает настройки логирования и Vulkan summary, но не меняет VSync или игровой FPS cap.

Записать минимум пять пар base/cap, чередуя порядок A/B и B/A; off проверить отдельно. Не смешивать первую компиляцию шейдеров с прогретыми проходами. Для каждого драйвера предварительно прогреть кэш. Зафиксировать частоты, температуру и фоновые приложения. Нулевые/недоступные датчики на Nouveau не считать реальными измерениями.

```bash
python3 bench/analyze_mangohud.py --per-frame logs/nvidia_run01/*.csv
```

Анализатор принимает только покадровые CSV (`log_interval=0`). Средний FPS = 1000 / средний frametime; 1% low = 1000 / среднее худшего 1% времён кадров. P99 выводится отдельно. Сравнивать результаты отдельных запусков и разброс между ними; не превращать тысячи зависимых кадров в тысячи независимых повторов. Не считать разницу 1–5% подтверждённой, если она сопоставима с разбросом проходов. Frametime не измеряет input-to-photon latency.

## Откат и текущие ограничения

Сборка ничего не устанавливает в систему. Для возврата к исходной политике локального патча убрать `NVK_GM107_CMD_CACHE_LIMIT_KIB` и перезапустить приложение. Для возврата к исходному NVK выбрать base ICD. Wrapper меняет переменные только внутри своего процесса.

Для возврата с Nouveau к NVIDIA потребуется штатная загрузочная запись NVIDIA. До её проверки переход к Nouveau не предлагается выполнять. LTS-пакет присутствует, но это ещё не проверенная резервная загрузка. Перед изменением загрузчика нужны его фактическая конфигурация, резервная копия и отдельное подтверждение. VBIOS/напряжения/лимиты не затрагиваются.

Этап E не выполнен: тестового GPU здесь нет. Этап D выполнен для host headless-сборки; целевая CachyOS/WSI-сборка и hardware validation остаются. Текущие ошибки NVKMS требуют отдельных данных о времени возникновения и фактических параметрах NVIDIA; этот патч их не исправляет.

Если политика не снижает реальный расход памяти — проверить число возвращаемых блоков и размещение BO. Если ухудшает frametime — увеличить лимит или оставить эксперимент выключенным. Следующая самостоятельная гипотеза: NAK/SM50, давление на регистры и лишние загрузки в конкретных шейдерах, с проверкой shader-db и GPU correctness.
