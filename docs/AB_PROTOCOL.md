# A/B-протокол для H2 и последующих NVK-патчей

Это план измерений, **не результат бенчмарка**. H2 описан в [NEXT_PATCH.md](NEXT_PATCH.md); флаг и новый GPU-микротест пока не реализованы. Здесь уже доступен только анализатор парных CSV.

## 1. Сборки и контроль

| Обозначение | Состав | Назначение |
|---|---|---|
| N | Установленный NVIDIA 580.196.07 | Конечный пользовательский эталон |
| A | Чистый Mesa `8e87a503ebd91408c88596d1b9eeb5f4c0b2088d` | Эталон NVK, без первого патча |
| B0 | Та же база + только новый H2, флаг off | Проверка того, что добавление кода само не меняет результат |
| B1 | Та же библиотека, что B0, H2 on | Измерение новой политики |

До основного теста сравнить A/B0: ожидается одинаковая компиляционная политика, корректное изображение и результат в пределах шума. Затем основное сравнение A/B1; B0/B1 полезно как дополнительное исключение различий сборки. Проприетарный N сравнивается с A и B1 отдельными boot blocks; его нельзя использовать вместо A для установления причинного эффекта конкретного патча.

Сборки A/B должны иметь одинаковые build options/toolchain. В новом launch wrapper потребуется собственный путь к H2 ICD: старый `bench/run-game.sh off|cap` выбирает **v0.1**, не H2. Пока не использовать его как готовый запуск второго эксперимента.

Для каждого запуска сохранить SHA-256 библиотеки и manifest, compiler flags, kernel/module, идентификатор варианта и фактически загруженный `libvulkan_nouveau.so` из `/proc/<game_pid>/maps`. `vulkaninfo` в родительском shell недостаточно: Steam pressure-vessel может менять ICD. Записывать только нужную строку maps и разрешённые экспериментальные переменные, не весь environment (он может содержать секреты).

## 2. Сначала установить механизм

Новый graphics microbenchmark должен генерировать offscreen изображение с полноэкранным triangle и fragment shader, читающим отдельные constant-offset UBO элементы. Данные генерируются на CPU, но неизвестны компилятору; итог readback сравнивается с CPU/reference. Использовать uint-операции и `R32_UINT` attachment для точной проверки, а floating-point игровой shader проверять отдельно. Поддержку формата/query/extension проверять до запуска.

Матрица, каждый параметр меняется отдельно:

- число статических UBO-чтений: 1, 4, 8, 16, 32;
- число draws на кадр: 1, 100, 1000; общую покрываемую площадь удерживать известной (например, scissor tiles) и записывать;
- неизменная привязка против смены UBO на каждом draw;
- constant offset против lane-dependent offset (отрицательный контроль, он не должен включать H2);
- ordinary descriptor set против push descriptors;
- 720p и 1080p — отдельные серии, не A/B с разным разрешением.

Размер UBO, число шейдерных операций, render target, barriers, размер submission и readback одинаковы для A/B. Для Dota-relevance дополнительно нужен shader/command capture реальной сцены; микротест сам по себе не доказывает игровой эффект.

GPU timing: query timestamps до и после одинакового участка graphics workload, проверка `timestampValidBits`, availability и пересчёт через `timestampPeriod`. Дожидаться результатов после завершения соответствующего fence; учитывать valid bits/wrap. Несколько итераций в batch снижают долю timestamp overhead. Измерять вне present/VSync. CPU record/submit/fence-wait — отдельные метрики; fence-wait нельзя назвать временем работы GPU или процентом загрузки.

Снять NIR/NAK/SASS и compiler statistics в диагностическом проходе. В базе есть `VK_KHR_pipeline_executable_properties` путь для instruction count, static cycles, max warps, spills/fills; тест должен проверить поддержку и включить capture-statistics flag при создании pipeline. GPR можно получить через инструментированный compiler report/NAK dump. Static cycles — модель компилятора, не аппаратные измерения.

Ожидаемый fingerprint H2: появляется дополнительная cbuf binding; некоторые global/address операции переходят в constant-buffer access/операнды; off совпадает с A; динамический контроль не меняется. Если fingerprint отсутствует — FPS-сравнение ещё не проверяет гипотезу.

Validation, NAK print, push dump, синхронный submit debug и детальные счётчики отключить в проходах производительности. При GPU fault или неверном readback остановить серию, сохранить ошибку, вернуться к base. Не продолжать собирать «быстрые» кадры с неверным изображением.

## 3. Dota 2: зафиксировать нагрузку

Один локальный replay текущей версии игры, SHA-256 файла, точный начальный tick, camera/player perspective и участок 120 секунд. Воспроизведение с одинаковой скоростью. Не использовать онлайн-матч, случайное вращение камеры или главное меню.

Основной профиль — **3 полосы качества**, поскольку именно на нём наблюдалась проблема. Фиксировать снимок всех individual settings: одинаковое название пресета не гарантирует одинаковые texture/shadow/AA/render-scale параметры. Render scale, FSR/upscaling, VSync, FPS limit и present mode одинаковы; лимит должен быть вне измеряемого диапазона, чтобы не скрывать эффект. Не менять настройки автоматически внутри тестового wrapper.

720p/minimum — отдельный диагностический контроль, а не источник цифры «ускорения» относительно 1080p/good. До тестов зафиксировать, действительно ли прежние 80–90 FPS относятся к этой паре разрешения/настроек.

Steam Overlay off. KWin workaround, два монитора, refresh rates и WSI-путь одинаковы внутри NVK A/B. MangoHud для логирования — отдельный слой, отличный от Steam Overlay; отдельно проверить, что включение MangoHud не вызывает артефакты/заметную деградацию. При таком эффекте использовать иной способ захвата, а не снимать испорченные кадры.

Не переключать фокус на терминал во время записи. Сбор телеметрии должен работать в фоне с одинаковым интервалом. Pstate и частоты только **читать** из доступных источников: этот протокол не записывает их и не выполняет reclocking. Использовать уже установленное и проверенное состояние для обеих NVK-сборок; если частоты различаются, пару не считать сопоставимой. Отсутствующий sensor записывать как `null`/`unavailable`, никогда как 0% или 0 MiB.

## 4. Прогоны

1. Подготовить отдельный shader cache для A, B0, B1. После изменения политики cache identity должен отличаться даже внутри одной библиотеки.
2. Прогреть каждый вариант одним и тем же полным replay segment минимум дважды. Если третий проход всё ещё заметно меняется из-за компиляции, закончить прогрев до измерений и записать это правило. Не включать cold compilation в warm-FPS метрику.
3. Зафиксировать 8 пар до просмотра результатов: AB, BA, AB, BA, BA, AB, BA, AB. Для каждой пары использовать новую сессию игры с тем же replay start. Всего 16 измеряемых запусков. A=base, B=B1.
4. Каждый запуск — одинаковый 120-секундный участок, покадровый MangoHud CSV (`log_interval=0`, `log_duration=120`). Старт логирования синхронизировать с выбранным replay tick, записывать фактическую границу и длительность. Ручное попадание в tick ограничивает чувствительность к 1%: для такого эффекта нужен автоматизированный старт/replay capture, а не округлённый FPS на глаз.
5. Любые пропуски/ошибки/смены фокуса фиксировать. Заранее недействительный запуск повторять вместе со всей парой; хранить исключённые исходники и причину. Не выбирать лучшие проходы и не исключать «медленные» без заранее определённой причины.
6. Отдельным сеансом повторить серию, если эффект мал или пограничен. Не добавлять по одной паре, пока CI не станет положительным. Если power недостаточна, заранее назначить размер следующей серии.

Горячая серия shader cache и отдельная холодная серия отвечают на разные вопросы. Input-to-photon latency здесь не измеряется: frametime не равен задержке ввода.

## 5. Сравнение с NVIDIA

После проверки B1 отдельно измерить N/A/B1 в тех же replay/настройках. Для N и NVK использовать, если возможно, одинаковую версию ядра из существующих загрузок; если не совпадает, это явно указанный системный конфаундер. Не менять загрузочные записи ради этого протокола.

Для конечного сравнения целого стека допускаются разные штатные clocks драйверов, но записываются температура, фактическая частота и метод её отчёта. Такое сравнение отвечает «какой стек быстрее на этой машине», а не выделяет чистую разницу shader compiler. Не нормировать FPS линейно на MHz и не объявлять частоты эквивалентными без проверки.

Чередовать boot blocks N → NVK → N, затем NVK → N → NVK при независимом повторе. Новый Nouveau boot block заново проверяет pstate; протокол его автоматически не повышает. Не смешивать cold-first N с warm-NVK. Сохранённая NVIDIA-загрузка остаётся способом восстановления.

Это шаблон, не запись проведённого теста. Перед публикацией удалить персональные пути/идентификаторы и не добавлять целые environment/journal dumps, бинарники драйвера и содержимое памяти. Issue #4 остаётся открытым: универсальный безопасный collector в этом изменении не реализован.

CSV manifest для нового анализатора:

```csv
pair,variant,file
01,A,raw/base_01.csv
01,B,raw/on_01.csv
02,B,raw/on_02.csv
02,A,raw/base_02.csv
```

Добавить все 8 пар. Пути относительны каталогу manifest, а не cwd. Одна запись на вариант в паре. `bench/results/` игнорируется Git; исходные данные хранятся локально, проверенные обезличенные результаты публикуются отдельным осмысленным commit.

```bash
python3 bench/compare_ab.py --per-frame bench/results/pairs.csv > bench/results/comparison.json
```

Команда проверяет структуру пар, повторное использование файла, покадровые данные, длительность 120 ±2 s. Она **не может** проверить тот же replay, активный драйвер, качество изображения, частоты, фокус или правильность `log_interval=0`; это отдельные обязательные проверки протокола.

- Средний FPS = `1000 / mean(frametime_ms)`.
- 1% low = `1000 / mean(худшего ceil(N × 0.01) frametime)`; p99 отдельно.
- Основной effect = геометрическое среднее парных отношений FPS(B)/FPS(A) минус 1.
- 95% CI — percentile bootstrap по **целым парам прогонов**, 20 000 повторов, фиксированный seed. Кадры не считаются независимыми экспериментами.
- Для p99 анализатор переворачивает отношение: положительное значение означает уменьшение p99.

Средний FPS — заранее выбранная основная метрика. CI дополнительных метрик описательные, без поправки за множество сравнений; нельзя выбирать задним числом метрику, которая дала плюс. Практический gate: эффект ≥1%, CI основной метрики выше нуля, корректность и стабильность подтверждены, нет воспроизводимого регресса хвостов. Если CI широк, вывод «неопределённо», а не «эффекта нет». Если воспроизводимо хуже, публикуем отрицательный результат и следующую гипотезу из NEXT_PATCH.
