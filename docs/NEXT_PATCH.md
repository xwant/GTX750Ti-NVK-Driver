# Следующий эксперимент: избирательное продвижение UBO в cbuf на GM107

> Реализация 10 ноября 2026: [H2_IMPLEMENTATION.md](H2_IMPLEMENTATION.md). Ниже сохранён исходный план; дополнительные ограничения и фактические проверки описаны в отчёте реализации.

Дата исследования: 2026-11-09. **Статус: проект изменения, не реализованный и не проверенный на GPU патч.** В этой ветке добавлены исследование, план реализации и инструмент сравнения A/B; существующий `gm107-command-cache.patch` не изменён.

## Решение

Следующий кандидат — изменить политику `build_cbuf_map()` в Mesa NVK: экспериментально разрешить **один обычный uniform buffer (UBO) во фрагментном шейдере GM107** переносить в аппаратный constant buffer, если он часто используется и все учитываемые обращения имеют постоянные смещения. Это изменение компиляции шейдера и привязки его ресурсов, а не настройка качества игры.

Это гипотеза H2, а не найденная причина низкого FPS Dota 2. Сначала измеряем применимость к её шейдерам. Если подходящих UBO нет, этот кандидат не способен ускорить данную сцену и его не следует долго тестировать в игре.

Рабочая база Mesa остаётся `26.2.6`, SHA `8e87a503ebd91408c88596d1b9eeb5f4c0b2088d`. Первый патч не включаем в новую экспериментальную сборку: иначе невозможно отделить эффекты двух изменений. Сравнение с NVIDIA остаётся отдельным обязательным этапом: выигрыш над исходным NVK ещё не означает выигрыш над NVIDIA.

## Аудит первого патча

v0.1 ограничивает список **возвращённых** LOCAL-capable блоков по 64 KiB в одном command pool. Не изменяет исполнение живого шейдера, выбор инструкций, текстуры, очередь GPU, GART/QMD-кэши. На base SHA выполнен `git apply --check`: успешно.

При `256` сохраняются четыре блока; остальные уничтожаются через существующий путь снятия ссылки. Это может уменьшить удержание памяти после всплеска. При постоянной перезаписи команд может, напротив, добавить выделения и VM-операции. `LOCAL` в `nvkmd_nouveau_mem.c` допускает VRAM и GART, поэтому нельзя переводить число освобождённых объектов напрямую в освобождённую физическую VRAM. CPU-тест 512 → 4 проверяет жизненный цикл имитированных объектов.

Имеющиеся отчёты подтверждают загрузку изменённой библиотеки, но не содержат контролируемого подтверждения, что лимит `256` был активен во всех игровых проходах. Наличие patched ICD и включение экспериментальной политики — разные проверки.

`vk_cache_probe.c` — тест передачи данных и возврата командной памяти, с CPU-временем и оценками memory budget. Он не проверяет скорость фрагментного шейдера и не годится как основной тест H2.

## Почему выбран этот участок

Проверены исходники точного base SHA и текущий снимок upstream main `5ecabeae8379ca8afb516921ca0fbde397583456`. В обоих сохраняется запрет из пункта 1 ниже. Это не утверждение об отсутствии всех связанных MRs: история и открытые обсуждения Mesa полностью не исследованы.

1. [`nvk_nir_lower_descriptors.c`, `build_cbuf_map`, строки 402–470](https://gitlab.freedesktop.org/mesa/mesa/-/blob/8e87a503ebd91408c88596d1b9eeb5f4c0b2088d/src/nouveau/vulkan/nvk_nir_lower_descriptors.c#L402): кандидаты сортируются по `use_count`. Но `NVK_CBUF_TYPE_UBO_DESC` на `cls_eng3d < TURING_A` всегда пропускается. Комментарий объясняет это ожидаемой стоимостью разбиения pushbuf при каждой привязке.
2. [`nvk_cmd_draw.c`, `nvk_cmd_flush_gfx_cbufs`, строки 4288–4391](https://gitlab.freedesktop.org/mesa/mesa/-/blob/8e87a503ebd91408c88596d1b9eeb5f4c0b2088d/src/nouveau/vulkan/nvk_cmd_draw.c#L4288): путь привязки до Turing **уже существует**. Для обычного descriptor set он подаёт 12 байт дескриптора через `nvk_cmd_buffer_push_indirect()` и MME. Это не отсутствующая аппаратная инструкция; сейчас путь ограничен политикой компилятора.
3. [`nvk_cmd_buffer.c`, строки 234–246 и 1297–1377](https://gitlab.freedesktop.org/mesa/mesa/-/blob/8e87a503ebd91408c88596d1b9eeb5f4c0b2088d/src/nouveau/vulkan/nvk_cmd_buffer.c#L234): indirect push завершает текущий push и ставит `no_prefetch`. Для push descriptors адрес можно получить из CPU-копии, поэтому этот частный случай не требует такого же разбиения. Обычные descriptors нельзя произвольно заменить CPU-снимком: их содержимое может корректно меняться после записи команд.
4. [`nvk_nir_lower_descriptors.c`, `lower_load_ubo_intrin`, строка 494](https://gitlab.freedesktop.org/mesa/mesa/-/blob/8e87a503ebd91408c88596d1b9eeb5f4c0b2088d/src/nouveau/vulkan/nvk_nir_lower_descriptors.c#L494): существующее преобразование проверяет окно cbuf и использует штатное lowering. Его нужно переиспользовать, сохраняя проверки границ и robustness.
5. [`nak/from_nir.rs`, обработка `ldc_nv`](https://gitlab.freedesktop.org/mesa/mesa/-/blob/8e87a503ebd91408c88596d1b9eeb5f4c0b2088d/src/nouveau/compiler/nak/from_nir.rs#L3521): постоянный cbuf index/offset может стать источником `CBufRef`; далее легализация SM50 допускает cbuf-операнды части ALU-инструкций. Это даёт возможность убрать отдельные загрузки и адресные вычисления. Не каждый load обязательно исчезнет: результат проверяется по сгенерированному коду.

Ожидаемый механизм: небольшая дополнительная стоимость привязки на draw против потенциального сокращения загрузок/адресных операций **для каждого фрагмента**. Возможны меньше инструкций и временных GPR, лучшее скрытие задержек. Выигрыш вероятнее при большом числе фрагментов на привязку; много мелких draws, смены UBO и нагрузка на constant cache могут дать регрессию.

`use_count` — число статических NIR-обращений на данной стадии компиляции, не число обращений за кадр и не профиль горячести. Постоянный адрес не означает постоянное значение: данные UBO остаются runtime-данными и не подменяются константами игры.

## Точное предлагаемое изменение H2

Первый прототип должен быть выключен по умолчанию. Предлагаемое, **пока не существующее** имя флага: `NVK_DEBUG=gm107_ubo_cbuf`. Обычная сборка не знает этого флага; сейчас запускать его бессмысленно.

Условия исключения из запрета pre-Turing:

- фактический chipset `0x117`, stage `MESA_SHADER_FRAGMENT`, эксперимент включён;
- обычный `VK_DESCRIPTOR_TYPE_UNIFORM_BUFFER` с compile-time постоянным индексом descriptor array; mutable, dynamic UBO и inline uniform blocks не расширяются этим экспериментом;
- все обращения к выбранному кандидату проходят консервативный анализ постоянного байтового смещения; неизвестные, wildcard и динамические смещения отклоняют кандидата;
- известный ненулевой диапазон целиком внутри существующего `NVK_MAX_CBUF_SIZE`; расчёты диапазона без переполнения;
- как начальный порог — `use_count >= 8`; это параметр гипотезы, **не измеренный оптимум**;
- не более одного дополнительного UBO на fragment shader; выбрать детерминированно по существующей сортировке;
- сначала сохранить все cbuf-привязки, которые выбрал бы upstream; новый кандидат получает только оставшийся слот. Не вытеснять root/descriptor-set/dynamic cbuf ради эксперимента;
- существующий `no_cbuf` имеет приоритет; compute/kernel и indirect-bindable shaders остаются на прежней политике.

Консервативная логика выбора, не готовый патч:

```text
map = build_exact_upstream_map()
if effective_gm107_flag && fragment && map_has_free_slot:
    candidate = first(sorted_candidates satisfying H2 checks)
    append(candidate)
lower_with_existing_code(map)
```

Не снижать задержки инструкций, не удалять Vulkan barriers/cache invalidation, не менять allocator, частоты или качество картинки. Графический путь binding остаётся штатным и обязан корректно отслеживать смену pipeline, descriptor sets и push descriptors.

| `nvk_physical_device.c` | Проверить, что существующее хеширование compiler flags разделяет pipeline/shader UUID и disk cache. Сам механизм уже есть, переписывать его не нужно |

Разделение shader cache обязательно: переключение флага в одной библиотеке иначе может повторно использовать старый shader binary и сделать A/B недостоверным. На время диагностического дампа отключать дисковый shader cache только для отдельного процесса; производительность измерять с прогретыми раздельными кэшами. Не удалять пользовательский Steam shader cache целиком.

## План реализации и условия перехода

**C0 — подтвердить применимость.** В отдельной диагностической сборке логировать на компиляции только shader hash/stage, обычные/динамические UBO, число кандидатов, постоянные/динамические смещения, причину отказа. Не выгружать содержимое буферов. На выходе нужен счётчик подходящих fragment shaders Dota на целевом пресете. Компиляционные счётчики не доказывают, что shader горячий или вообще участвует в измеряемой сцене: это проверяется захватом/replay команд или инструментированием привязки. `NAK_DEBUG=print` и push dumps — только отдельные диагностические проходы, не FPS-измерения.

**C1 — implement.** От чистого Mesa SHA создать отдельную ветку `experiment/gm107-ubo-cbuf`, добавить флаг, анализ и выбор, cache-key separation, NIR-тесты. Не наслаивать на cache-limit patch. Привязку cbuf использовать существующую; при обнаружении проблемы в ней исправление оформлять отдельно.

**D1 — CPU/compiler correctness.** Набор случаев: флаг off; иной chipset; VS/CS; 7 и 8 статических обращений; динамический descriptor index; динамический byte offset; смешанные обращения; выход за cbuf window; mutable descriptor; push descriptor; заполненные слоты; `no_cbuf`; indirect bind; robustness. Проверить off output against base, ожидаемое число slots, сохранность всех ранее выбранных slots, детерминизм. Проверить отдельные UUID/cache entries при переключении флага.

**D2 — сборка CachyOS.** Три приватных build dirs: исходный NVK, новый NVK с runtime opt-in off/on (одна новая библиотека), без установки. Тот же фиксированный SHA, compiler/toolchain, build options и зависимости. Существующий `build-cachyos.sh` собирает v0.1, поэтому для H2 нужен отдельный скрипт, а не запуск существующего с ожиданием второго патча. Записать dirty diff, SHA патча, SHA-256 библиотек, `meson introspect --buildoptions`, версии зависимостей; `meson test --suite nouveau`. CPU-тесты не заменяют аппаратную проверку.

**D3 — аппаратный микротест.** Новый offscreen graphics-тест с обычным UBO, постоянными смещениями и проверяемым результатом RGBA/readback. Сравнить base/off/on. Проверить обновление UBO между draws, разные offsets/ranges, смены pipeline и descriptor sets, null/OOB при включённой robustness, push descriptors; GPU validation в отдельном проходе. Далее выполнить затрагиваемые Vulkan CTS UBO/robustness/descriptor cases, не заявляя полной conformance по одному микротесту.

**E — измерение.** Следовать [AB_PROTOCOL.md](AB_PROTOCOL.md). Сначала механизм и GPU-время микротеста, затем Dota с тем же изображением, затем отдельные boot blocks с NVIDIA. Критерии успеха/отказа ниже.

## Метрики, критерии и отрицательный результат

Основная метрика для Dota: средний FPS на фиксированном 120-секундном участке replay при неизменном качестве. Дополнительные: 1% low по худшему 1% frametimes, p99 frametime, GPU-time микротеста, CPU record/submit time, GPR/spills/instruction count, объём/число push segments. Доступный memory budget — вспомогательная оценка, не прямое измерение физической VRAM или выгрузок.

Промежуточный успех H2: изменение реально применяется к используемому shader; корректность сохранена; повторяемое ускорение относительно **base NVK**, включая контроль новой библиотеки с флагом off. Итоговый успех проекта требует отдельного результата против **NVIDIA** с тем же качеством/сценой; разные штатные clocks записываются и не скрываются. Снижение качества не считается результатом патча.

Предварительно фиксируем целевой размер эффекта ≥1%, минимум 8 пар в порядке AB/BA, 95% парный bootstrap CI не пересекает ноль для основной метрики; p99/1% low не должны давать воспроизводимый существенный регресс. Малое число пар и систематические ошибки не исчезают от bootstrap: сомнительный 1–5% эффект перепроверить независимым сеансом. Не выдавать CI за доказательство отсутствия конфаундеров.

| Отрицательный результат | Вывод и следующая проверяемая гипотеза |
|---|---|
| В рабочей сцене нет подходящих UBO | H2 не применима к Dota здесь. Перейти к shader statistics и NAK pressure/scheduling; не снижать порог до получения «положительного» FPS |
| Код shader улучшился, но GPU-time не изменился | Эти операции не ограничивают тест или эффект ниже шума; измерить hot draw/другой тип нагрузки |
| Большие draws быстрее, мелкие медленнее | Стоимость indirect binding превышает экономию. Отдельный H2b: исключение только для push-descriptor layout, где адрес доступен напрямую; сначала проверить его использование игрой |
| Возникли stale data/robustness failures/артефакты | Остановить perf-тесты; восстановить base ICD, минимизировать repro. Не ослаблять проверки ради FPS |
| NVK ускорился, но всё ещё уступает NVIDIA | Частичный результат разработки; цель превосходства NVIDIA не достигнута |
| Spill-heavy shader, но UBO-выигрыша нет | NAK: исследовать размещение load/ALU относительно пиков liveness. В базе уже есть occupancy-aware scheduler — нельзя заявлять, что мы добавляем его с нуля |
| Связь провала с image/texture workload | Отдельно исследовать NIL tiling/compression/format path и GPU captures; не переносить на GM107 возможности GM204 или Turing |

## Остальные узкие места и почему они не первый патч

- **NAK SM50 latency model.** `sm50.rs` прямо содержит приблизительные RAW/WAR/WAW latency assumptions. Перспективное направление, но уменьшение задержек «на глаз» способно сломать данные. Нужны dependency microbenchmarks и hardware correctness, прежде чем менять числа.
- **Register pressure.** `opt_instr_sched_prepass.rs` уже учитывает occupancy cliffs и давление GPR, `assign_regs.rs` уже имеет spill logic. Произвольный лимит регистров может увеличить spilling. В [NVIDIA Maxwell Tuning Guide](https://docs.nvidia.com/cuda/maxwell-tuning-guide/index.html) отдельно отмечена необходимость баланса occupancy/spills и особенности local-load cache. Не путать этот баланс с отсутствием register scheduling.
- **Кэш global loads.** В `nak/ir.rs`, `LdCacheOp::select()` для `MemOrder::Constant` на SM50 уже выбирается `CacheIncoherent`. Идея «просто включить readonly cache» не является новой оптимизацией этой базы. GM107 и GM204 различаются, в том числе возможностями кэширования обычных global loads.
- **VRAM/TTM.** 2 GiB — существенное ограничение, но в поздних NVK-тестах нет надёжных данных о residency/evictions. Нельзя считать 4.3 GiB RSS игры расходом VRAM. Изменение placement без этих данных рискует перегрузить PCIe.
- **Queue/barriers.** Накладные расходы возможны, но нет trace доказательства лишних ожиданий. Удаление WFI/barriers без проверки зависимостей не предлагается.
- **GPU utilization.** В upstream Linux v6.18 у `nouveau_driver_fops` нет `.show_fdinfo`; это конкретный повод проверить отсутствие DRM engine counters, но не доказательство состава CachyOS 6.18.55 со всеми его патчами. [Исходник](https://github.com/torvalds/linux/blob/v6.18/drivers/gpu/drm/nouveau/nouveau_drm.c#L1323). Реальные counters и поддержку KDE нужно проверить отдельно. Время между submit и fence включает ожидание и не является честным процентом GPU busy. Не синтезировать «загрузку» из FPS.

## Безопасность и фактическая проверка этого этапа

Чтение GitHub/исходников, локальная проверка применимости v0.1 и тесты анализатора не требуют изменения тестового ПК. В этой ветке нет установки драйвера, изменения Limine/initramfs, записи pstate, VBIOS или системных конфигураций.

H2 ещё не собран и не запускался. GPU здесь недоступен. Для будущего запуска используется уже существующая экспериментальная Nouveau-загрузка; стабильная NVIDIA-загрузка сохраняется. Любое новое действие, способное нарушить загрузку/графическую сессию, требует согласия пользователя. Откат runtime-эксперимента: закрыть приложение, выбрать base ICD, убрать новый флаг и снова запустить; при зависании воспользоваться уже проверенной NVIDIA-загрузкой. Конкретные действия с boot files не входят в этот этап.

Результаты проверки инструментов этого изменения будут записаны в `docs/VALIDATION_V2_PLAN.md`. Старые журналы `logs/` и `RESULTS.json` остаются историческими и не являются тестами H2.
